# VIMS Opportunity Board — November 10, 2026 update

## What's included

- Brand palette and high-contrast inactive/active navbar tabs.
- Prominent disclaimer on browse page: independent board created/maintained by Robert Isdell, not an official institutional opportunity service.
- Updated About text: opportunities offered by members of the VIMS & Batten School community.

- Automatic, non-destructive database schema migration for the added change-request and notification columns.

## Administrator GUI: private SSH tunnel (no public symlink!)

The administrative app lives at `/home/risdell/vims-opportunity-board-vims/admin/app.R`. **Do not symlink `admin/` under `/srv/shiny-server`; that would make it publicly accessible without authentication.** It is intentionally separate so W&M SSO can replace this temporary access method later.

Have IT create a strong, random administrator password in a root-owned configuration file, readable only by `shiny`:

```bash
sudo install -d -o root -g shiny -m 750 /etc/vims-opportunity-board
sudo install -o root -g shiny -m 640 /dev/null /etc/vims-opportunity-board/admin.env
sudo nano /etc/vims-opportunity-board/admin.env
```

Contents (example only, choose your own secret):

```text
OPPORTUNITY_ADMIN_PASSWORD="a-long-random-unique-password"
```

For occasional manual use, on the server:

```bash
cd /home/risdell/vims-opportunity-board-vims/admin
sudo -u shiny Rscript -e "shiny::runApp('.', host='127.0.0.1', port=4862, launch.browser=FALSE)"
```

Leave it running. On your workstation, open a separate terminal:

```bash
ssh -N -L 4862:127.0.0.1:4862 risdell@shiny.vims.edu
```

Then navigate on your workstation to `http://localhost:4862` and sign in with the password from `admin.env`. This gives you an actual browser GUI but no exposed management endpoint. Access to a loopback-only app still requires trust in other shell users on the host, and the password is an additional control.

If you'd like this GUI to run continuously, IT can create a systemd unit bound to `127.0.0.1`; see the included sample at `deploy/vims-opportunity-board-admin.service`. Do not serve it on a public interface without server-side SSO/access control.

### What the admin GUI does

- Lists pending records first, then other postings.
- Allows edits to titles, descriptions, dates, contacts, compensation, and other fields.
- Saves/approves/closes postings. Approval enforces all four valid dates.
- Reviews change/removal requests; marks them resolved/dismissed **after** verifying the request and separately editing the posting.

## Email notifications (optional until IT provides mail settings)

The app now queues a notification when a new opportunity or change request is inserted. No mail is sent until an institutional SMTP relay is configured and the cron job enabled.

In consultation with IT, create `/etc/vims-opportunity-board/mail.env` with group-readable `shiny` permissions (root owner, mode 640):

```text
OPPORTUNITY_SMTP_SERVER="smtp://YOUR-APPROVED-RELAY:587"
OPPORTUNITY_SMTP_TLS="force"
OPPORTUNITY_MAIL_FROM="APPROVED-SENDER@vims.edu"
OPPORTUNITY_NOTIFY_TO="risdell@vims.edu"
# Only if the SMTP server requires authentication:
# OPPORTUNITY_SMTP_USER="..."
# OPPORTUNITY_SMTP_PASSWORD="..."
```

Use `smtps://HOST:465` for implicit TLS, or an internal trusted mail relay with IT-approved settings. Do not commit these settings to GitHub. The `curl::send_mail()` function uses the R `curl` package and sends the configured plain-text email via SMTP; SMTP accepting a message doesn't guarantee delivery to Inbox.

Test queued notifications manually:

```bash
cd /home/risdell/vims-opportunity-board-vims
sudo -u shiny Rscript scripts/send_notifications.R
```

When mail works, add a per-minute **shiny user's crontab** (run `sudo crontab -u shiny -e`):

```cron
* * * * * cd /home/risdell/vims-opportunity-board-vims && /usr/bin/flock -n /var/lib/vims-opportunity-board/notification.lock /usr/bin/Rscript scripts/send_notifications.R >> /var/lib/vims-opportunity-board/notification.log 2>&1
```

Pending emails persist until SMTP successfully accepts them. Existing opportunity rows are automatically marked as notified on first migration; CSV imports are likewise marked as historical. If SMTP is not configured, submissions still work and simply remain queued. To troubleshoot, view `/var/lib/vims-opportunity-board/notification.log` (protected in the `shiny`-owned data directory).

## Notes for future SSO

The database retains `owner_id` and `owner_email` columns. A later W&M-SSO management app should populate `owner_id` from the **trusted identity assertion**, not user-entered email. Only then can authenticated submitters update their own listings; automatic publication is a separate policy decision. Keep the public browsing app unauthenticated.
